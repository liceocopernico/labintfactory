Design proposal · draft 0.8

LabDaemon Desktop

LabDaemon is a standalone Windows and Linux application for school lab instruments. A small Qt-free core runs three layers of plugins: transports, devices and experiments. A PySide6 interface on top offers a guided mode for first runs and students, and an expert mode for everything after.

Replaces the ipywidgets apps in labintfactory 0.1.1 Stack Python ≥ 3.14 · PySide6 · pyqtgraph · numpy · pyserial Date 28 September 2026

How to review. Settled choices carry a Decision label. All open questions are now answered; §14 lists what to verify first, in M0. In the mockups (§8), the numbered markers 1 refer to the notes under each figure.

What changed in draft 0.8: the real photometer, as found and built in M1.

  • One LED, not four. The photometer has a single LED driven by the board's 12-bit DAC. Its colour is whichever LED is fitted. The protocol is now LED <power>, plus LEDCOLOR <colour>, which records the fitted LED in EEPROM so the app knows its power range and stores it with every measurement (§4.4, mockups 2 and 9).
  • Arduino UNO R4 Minima. The photometer board is an UNO R4 (Renesas RA4M1), not a classic AVR Uno. It is now in the platform table: its serial number comes from the chip's factory ID, and it does not reset when the port opens, so the app checks readiness with PING (§4.4).
  • Next goal: a multi-LED photometer board with LEDs the firmware can switch between, which brings back colour selection by command (§13).
  • M0 and M1 status in the roadmap, and the results of early checks C1 and C3 (§13, §14).
  • Draft 0.7 aligned the mockups' colours with the implemented theme (§7.5).

1Goals and non-goals

Goals

  • Parity first: the photometer (absorbance, kinetics) and magnetic-field-profile labs run on real hardware on both platforms.
  • A new device or experiment means adding one plugin. No edits to the core or the GUI.
  • Any microcontroller whose firmware follows the LabInt wire protocol can be connected; only a device plugin is needed on the PC side.
  • The UI never freezes, and no call can hang on a silent device: every I/O operation has a deadline.
  • Every measurement is saved with its context (devices, settings, calibration, times) and can be reopened later.
  • The same experiment logic runs in the GUI, in Jupyter and in tests with simulated devices.

Non-goals for v1

  • Networked or remote acquisition (the old option C). The core keeps it possible later.
  • High-rate acquisition. The target is ≤ 100 samples/s per device; buffered streaming can come later.
  • Real access control. Student mode is a convenience lock, not security.
  • Plugin sandboxing. Plugins are trusted Python code.

Dependency rules

  1. labdaemon.core never imports gui, PySide6 or pyqtgraph. A test enforces this by importing the core with Qt blocked.
  2. Plugins depend on the core only. A plugin's optional gui.py may import Qt and labdaemon.gui.widgets. The core loads it lazily, by name, only inside the GUI.
  3. The GUI never calls a device or transport directly. It goes through the device manager's handles, so every call lands on that device's worker thread.
  4. Experiments reach devices only through capabilities (LightSensor, LinearActuator, …), never through a concrete device class.
  5. Plugins do not import each other. Code two plugins need goes into the core, for example core.analysis.linear_fit.

4Core

4.1Capabilities

Capabilities are small typing.Protocol interfaces with typed results. An experiment declares the capabilities it needs; a device declares the ones it provides. One device can provide several: the photometer board is both a LightSensor and a LightSource. The same absorbance experiment would then work with a Vernier light sensor, or with a simulated one.

4.2Parameters

Devices and experiments describe their settings as Parameter objects. The GUI generates forms from them, wizards pick subsets of them, and Jupyter users get validation for free. A ParameterSet holds the current values and is the single source of truth: widgets bind to it and never keep a copy of their own. This removes the "slider shows one value, code uses another" class of bugs found in the current code.

@dataclass(frozen=True)
class Parameter:
    key: str                          # "led_power"
    label: str                        # translatable: _("LED power")
    type: type                        # int | float | str | bool
    default: Any
    unit: str | None = None           # "ms", "mm", "mol/L"
    choices: Sequence | None = None   # e.g. gain: (1, 25, 428, 9876)
    minimum: float | None = None
    maximum: float | None = None
    step: float | None = None
    advanced: bool = False            # hidden in guided and student mode
    help: str = ""

Limits can depend on other values. The allowed led_power range depends on led_color, so after every change the device recomputes parameters() and the form updates only the affected field. Out-of-range values are rejected with a message rather than silently clamped.

A new board then needs only its firmware and a device plugin; transports, discovery, stopping, error handling and the raw console work unchanged. The old … executed protocol is not carried over; the existing boards are reflashed during M1 and M3.

Protocol rules (version 1)

  • Lines. ASCII lines ending in \n (\r\n is accepted), at most 160 bytes. UART boards default to 115 200 baud; USB CDC boards ignore the rate. Values containing spaces are double-quoted.
  • Addressing. Commands for a function carry its name as a prefix: thermometer:READ?. Board-level commands have no prefix. On a single-function board the prefix is optional, so simple sketches stay simple. Replies and events from a function include fn=….
  • One command at a time. The host waits for each reply before sending the next command. While one function is running an operation (after BUSY), the board still accepts commands for its other functions, plus STOP, STATUS? and PING.
  • Commands. VERB arg …. Verbs are upper case and queries end in ?. Numbers always use . as the decimal separator, whatever the PC's locale.
  • Replies start with OK, BUSY or ERR. Payloads are key=value pairs, so they describe themselves, their order doesn't matter, and the host ignores keys it doesn't know. This keeps old apps compatible with newer firmware.
  • Errors. ERR code message. The standard codes are 1 unknown command, 2 bad argument, 3 out of range, 4 busy (or owned by another host), 5 not ready (for example "not homed"), 6 hardware fault, 7 not supported and 8 not authorised. Codes from 100 up are model-specific.
  • Events. EVT name key=value … lines can arrive at any time: EVT DONE, EVT STOPPED, EVT LIMIT, EVT FAULT, and EVT BOOT when the board restarts.
  • Debug lines. Lines starting with # go to the device log and never break parsing, so firmware authors can print freely while they develop.
  • Timing. A command must reply within 500 ms. Anything slower must answer BUSY at once and finish with an event. During a BUSY operation the host sends STATUS? every second; a board that stops answering is marked Lost.
  • Versioning. ID? reports proto=1. New commands and keys are additive; only a breaking change raises the protocol number. The app supports the current and the previous version.

PC side: WireClient

The board owns one WireClient, and each device gets a FunctionChannel from it that adds the prefix, so plugin code just writes self.wire.query("READ", 3).

  • query(verb, *args, timeout=0.5) returns a Reply with typed accessors (.int("bb"), .float(), .bool()). A missing key raises BadReply, and ERR becomes DeviceError(code, message).
  • start(verb, *args) expects BUSY and returns an Operation: a future completed by the matching DONE, STOPPED or LIMIT event (§4.5).
  • Unsolicited events are dispatched to the device named in fn=: LIMIT and FAULT change its state and show in the GUI, and BOOT re-initialises the whole board.

Arduinos that reset when the USB port opens announce themselves with EVT BOOT. The client waits for that event (at most 3 s) instead of sleeping for a fixed time.

4.5Threads: one worker per connection

Your "one worker thread per device" rule, made precise for combined boards: the worker belongs to the connection, because that is what cannot be shared. A single-function board or a Vernier sensor gets exactly one worker. The photometer and thermometer of a combined ESP32 share their board's worker, and their commands are interleaved on it.

class BoardWorker:
    """The only thread that ever touches its board's transport and devices."""
    def submit(self, fn, /, *args, urgent=False, **kw) -> Future: ...  # urgent jobs (STOP) jump the queue
    def call(self, fn, /, *args, timeout=None, **kw): ...              # submit + wait (runner thread, Jupyter)
    def proxy(self, device) -> DeviceProxy: ...                        # same capability methods, each one a call()
    def start_polling(self, device, interval_s: float): ...             # live values → sample event
    def shutdown(self): ...

    def _loop(self):
        while not self._stopping:
            self._read_incoming()        # replies; EVT → complete Operations, notify devices; "#" → log
            job = self._next_job(timeout=self._until_next_deadline())
            if job: self._execute(job)   # result or exception → job.future; updates device state
            self._run_due_polls()
            self._send_heartbeats()      # STATUS? while any Operation is pending
  • Calls to one board are serialized, so two callers can never interleave bytes on the same link.
  • Polling runs between queued jobs, so a live reading never delays a "Set power" click.
  • Long operations never block the worker. start() sends the command, receives BUSY and returns an Operation at once. The worker keeps serving the board's other functions, polling and STOP while the stepper moves, and completes the Operation when its event arrives.

Experiment code receives proxies. self.sensor.read_light(3) looks like a direct call but runs on the board's worker. When a device method returns an Operation, the proxy waits for it on the caller's thread. The same experiment code therefore runs unchanged in the GUI (on the runner thread), in Jupyter and in tests.

Stopping a move

Stop is immediate. If the run is cancelled (Stop button, Esc) while a proxy is waiting on an Operation, the proxy submits the device's stop() as an urgent job. That job jumps the queue, and the worker is never stuck in a wait, so STOP reaches the board within milliseconds.

class StepperActuator(Device, LinearActuator):
    def move_to(self, mm: float) -> Operation:
        return self.wire.start("MOVE", f"{mm:.3f}")     # ← BUSY; returns at once

    def stop(self) -> None:
        self.wire.query("STOP")

self.actuator.move_to(z)    # proxy waits for EVT DONE; on cancel it sends STOP (urgent)
                            # EVT STOPPED → Interrupted(position), EVT LIMIT → LimitReached(side, position)

4.6Experiments: actions and runs

An experiment is a Qt-free controller class that holds state and exposes two kinds of operations:

  • @action: a short operation that returns a result, for example "measure blank" or "measure this standard".
  • @run: a long acquisition that records into a dataset until it finishes or is stopped, for example kinetics or a field scan.

The wizard and the expert panel are two views that call the same operations. Declaring them also lets the GUI build a generic expert panel: a plugin with no Qt code at all still gets a parameter form, action buttons, run controls, a plot and a table.

    ...

RunContext provides cancelled, elapsed (monotonic seconds since the run started), interruptible sleep/sleep_until_next, progress(fraction, text) and warn(message). Stopping a run cancels the context; any device operation the run is waiting on receives an urgent STOP (§4.5).

4.7Data, sessions and calibrations

  • Channel(key, label, unit) and Dataset: columnar, numpy-backed, append-only while recording, with a thread-safe append and a row_added event. Exports: to_csv, to_numpy and to_pandas (pandas is optional). The time column t is seconds since the run started; the absolute start time is stored as ISO 8601 with a time zone.
  • Session holds everything one lab produces: the experiment id and version, the mode used, parameter values, a device snapshot (board, function, link, firmware and settings at start), the calibrations used, datasets, notes and a log. 4.8Events, errors and logging

  • core.events.Signal (connect, disconnect, emit) runs callbacks in the emitting thread. The GUI bridge re-emits them as queued Qt signals so widgets update on the GUI thread; in Jupyter they are plain callbacks.
  • Exceptions share one hierarchy. LabError is the base, with TransportError (PortNotFound, PortBusy, PermissionDenied), ProtocolError (ProtocolTimeout, BadReply, UnsupportedProtocol), DeviceError (carries the ERR code; subclasses LimitReached and Interrupted), PluginError and ExperimentError (for example NotReady: "Measure the blank first"). Each error carries an actionable user message and a technical detail. For example: "Permission denied on /dev/ttyUSB0. Add your user to the dialout group, then log out and back in."
  • Logging stays on loguru, with three sinks: a rotating file in the user log folder, the GUI log dock, and the session log, which is saved with the data.

Where folder plugins are searched

Loading pipeline

  1. Collect entry points and manifests. Nothing is imported yet, so listing is fast and safe.
  2. Check api against core.API_VERSION. A mismatched plugin is listed as incompatible and not loaded.
  3. Import the plugin. A failure marks that plugin Error with its traceback in the Plugins view; the app starts anyway.
  4. Validate: metadata present, capabilities declared and actually implemented, requirements that point to known capabilities, unique ids.
  5. Register. A folder plugin with the same id as a built-in one overrides it only in developer mode, and a banner says so. This lets you test a new version of a built-in plugin without touching the installed app.

Developer tooling

  • Reload development plugins (Plugins view) reimports folder plugins whose devices and experiments are not in use.
  • labdaemon plugin new device|experiment <name> creates a working skeleton in the plugin folder.
  • labdaemon plugin check <path> validates the manifest, imports the plugin, checks capability conformance, and runs every action against simulated devices. It is useful once other authors join.

7.2Several experiments at once: leases

Decision Experiments open in tabs, and several can record at the same time, for example kinetics on Bench-5's photometer while a field scan runs on Rail-1.

  • A lease is the exclusive right to control one device (one function of a board). An experiment takes leases when its devices are assigned, and releases them when its tab closes or a device is reassigned.
  • Watching needs no lease. The Devices view and other tabs can show live readings from a leased device. One polling loop feeds every viewer.
  • Conflicts are explicit. Asking for a leased device shows who holds it. If the holder is idle, Take over moves the lease and the other tab shows "device released". If the holder is recording, the request is refused with the way out: "Stop the run in ‘Kinetics’ first."
  • Combined boards. Leases are per function, so the photometer and the thermometer of one ESP32 can serve two different experiments. Their commands interleave on the board's worker (§4.5).
  • Stopping. Esc stops only the current tab's operations, using fn:STOP for its own devices. Stop everything (toolbar, Ctrl+Shift+Esc) sends STOP to every board.
  • Tabs show a recording dot, and status-bar chips name the lease holder. Hidden tabs keep recording and buffering, and redraw their plots when shown.

The compiler's board identifier (FQBN) comes from the board's ID? reply through a built-in table: uno-r4-minima → arduino:renesas_uno:minima, uno → arduino:avr:uno, esp32 → esp32:esp32:esp32, teensy41 → teensy:avr:teensy41, and so on. The teacher can override it, and the choice is saved with the board.
  • Upload sequence.
    1. Check leases. If an experiment is recording with the board, the upload is refused with the way out ("Stop the run in ‘Kinetics’ first"). Idle leases are paused.
    2. Close the board's connection; its worker stops.
    3. Upload over USB.
    4. Reconnect, wait for EVT BOOT, and check that ID? reports the new firmware version.
    5. Run the firmware check, show the result, and resume the paused leases.
    Boards connected only by Wi-Fi or Bluetooth are asked to be plugged in by USB; over-the-air updates for ESP32 can come later.
  • Board support. "Install board support…" runs arduino-cli core install, adding the extra package URLs for ESP32, STM32 and Teensy, and shows progress and disk use (the ESP32 core takes a few hundred MB). In a central install, the policy can point arduino-cli at a shared data folder so each account doesn't download its own copy.
  • Sketches. Reference sketches ship with each release and are read-only. "Save as copy" puts an editable copy in Documents/LabDaemon/firmware. "New sketch from template…" asks for the board and its functions (for example photometer + thermometer), then generates both the sketch, with those functions declared, and a matching device-plugin skeleton in the plugin folder.

Editor: Monaco through qtmonaco

  • Loaded on demand. The web engine and Monaco start the first time the Firmware view opens, so the rest of the app never pays their memory cost.
  • Language server. For the open sketch, LabDaemon starts arduino-language-server (which runs clangd) with the sketch's board identifier and arduino-cli settings. A small local WebSocket bridge relays its messages to Monaco. This is how Arduino IDE 2 itself edits sketches, so teachers get the same completion and error checking (early check C5).
  • Compiler errors appear both in the Problems list and as markers in the editor. Ctrl+B compiles and Ctrl+U uploads.
  • "Open in Arduino IDE" is always available, for the IDE's serial plotter or library manager, for example.
  • Fallback. If the language server is missing, the editor keeps colouring and compiler markers without completion. If the web engine can't start, a plain text editor with the same Compile and Upload buttons is used.
  • Student lock. The Firmware view is for teachers only (§6.1).

7.4Hardware sheets: what the sensor is and what the numbers mean

Decision Every device plugin describes the hardware behind it: parts, key datasheet figures, charts, and how raw values become the measured quantity. The Devices view shows this on a Hardware tab (mockup 9), next to a live operating point. That operating point turns the current settings and readings into terms a teacher or student can act on: how close the sensor is to saturating, how fine the resolution is, and what to change.

  • Specs are data, not prose. Because the figures are structured, the plugin's own code uses them: the saturation check reads full_scale_counts instead of a hard-coded constant. The GUI and the Jupyter facade read the same file, so what the teacher sees and what the code does are always the same.
  • Operating point. A device can implement operating_point(), which returns a few labelled values computed from its current settings and last reading. For the photometer:
    • each channel as a percentage of full scale;
    • the resolution in lux per count;
    • the light level at which it would saturate;
    • hints such as "switching to gain 428× would saturate at about 160 lx".
    It runs on the board's worker thread like any other device call, and is refreshed with each live reading.
  • The board confirms its parts. An optional function command, HW? (for example OK sensor=tsl2591 led=red), lets one plugin support variants, such as an older photometer built with a TSL2561. The plugin then shows the right sheet and uses the right lux formula. Without HW?, the plugin's default parts are assumed and marked "not confirmed by the board".
  • Datasheets. The link to the manufacturer's page is always shown. A PDF copy ships only where redistribution is allowed. A teacher can also attach their own copy, stored in the data folder or the shared folder set by the policy, so it works offline in class. PDFs open in a built-in viewer (Qt PDF, part of PySide6-Addons, which the Firmware view already needs), or in the system viewer.
  • Notes are short Markdown explanations per language, rendered on the tab. Wizard steps can link to a section, for example a ParametersStep's "What do gain and integration time do?".
  • Vernier sensors. Their sheets link to Vernier's product pages. Ranges and resolution come from what godirect reports about each sensor channel.
  • Students see it too. The Hardware tab is read-only and stays visible when the student lock is on, because it is teaching material.
  • From Jupyter: photo.hardware.specs["full_scale_counts"], photo.hardware.chart("spectral_response") (a table) and photo.operating_point().

Platform details

  • Config, data (calibrations, plugins, recovery files) and log folders come from platformdirs, plus the machine-wide folders above.
  • Boards are remembered by serial number, not by COM number, IP address or Bluetooth address.
  • USB on Linux: a PermissionError produces the dialout/uucp group hint. On Windows, some Arduino clones need the CH340 driver; the Devices view links to it when no port shows up.
  • Bluetooth: Windows 10 or later, or BlueZ on Linux, and a Bluetooth LE adapter. One scanner serves both Vernier sensors and ESP32 boards.
  • Wi-Fi: lab PCs reach the boards directly. mDNS works only within the PC's own network, so boards elsewhere are added by IP address. The central installer adds a Windows firewall rule for mDNS (UDP 5353), which a per-user install asks for the first time it searches.

Packaging

  • Development: uv run labdaemon.
  • One PyInstaller one-folder build per platform feeds all the installers. It must run with --copy-metadata labdaemon, otherwise entry points do not resolve in the frozen app.
  • In the installed app, folder plugins can use only the libraries bundled with it. The Plugins view lists them.
  • scipy adds roughly 40 MB. Excluding submodules the app doesn't use (scipy.io, scipy.signal, …) keeps that down; the real saving will be measured in M4.

Firmware tools

  • In the app: the Firmware view (§7.3) uses arduino-cli, found inside Arduino IDE 2, on the PATH, or at a configured path.
  • For development and CI: PlatformIO builds every reference sketch for every board, for example pio run -e esp32dev -t upload.
  • Each release ships precompiled reference firmware for AVR and ESP32, with avrdude and esptool, so "Update firmware…" works without any compiler installed.
  • The LabInt library is also published as a zip for the Arduino IDE.

11.3Python version and distribution

  • Python 3.14 or newer (requires-python = ">=3.14"; .python-version moves from 3.13 to 3.14). The installers bundle their own Python, so lab PCs need nothing installed beforehand.
  • The standard build, with the GIL. The worker threads spend their time waiting for I/O, where the GIL is released, so the free-threaded build would gain nothing here and not every dependency supports it yet. Nothing in the design stops a later switch.
  • Not on PyPI. Each release publishes the installers and a wheel on the project's GitHub releases. For Jupyter or scripts, install into that environment from a checkout (uv pip install -e ".[jupyter]") or from the release wheel.

12Testing and quality

  • Protocol tests run WireClient against the WireSimulator and scripted transcripts: normal replies, ERR codes, events arriving between replies, # debug lines, a silent board (must time out), STOP during BUSY, a board that reboots mid-session, and a port that disappears.
  • Links: the TCP transport is tested against a WireSimulator served on localhost, including mDNS records and AUTH. The BLE transport is tested with a fake bleak client that splits lines across notifications. The same board seen on two links must be listed once.
  • Firmware: CI compiles every sketch for every board environment (AVR, ESP32, STM32, Teensy) and runs the parser unit tests in the PlatformIO native environment. firmware check runs the conformance suite against real boards.
  • Leases and policy: take-over and refusal rules, per-function leases on combined boards, and policy values overriding user settings.
  • Translation check: CI fails when a built-in string has no Italian translation (§7.1).
  • Device and experiment tests run against simulated devices. For example, the simulated photometer follows Beer–Lambert, and the absorbance test checks that the fitted slope recovers ε.
  • Plugin conformance: one parametrized test runs every registered plugin through the same checks as plugin check.
  • Architecture test: importing labdaemon.core with PySide6 blocked must succeed (rule R1).
  • GUI smoke tests (pytest-qt): open every experiment in both modes with simulated devices, run one action, and save.
  • Hardware tests are marked @pytest.mark.hardware and skipped by default.
  • CI: GitHub Actions on Ubuntu and Windows, Python 3.14, running ruff, pyright and pytest. Installers and the wheel are built on release tags.
